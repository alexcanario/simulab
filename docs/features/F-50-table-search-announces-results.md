# Table search announces results

## Summary
The search box of `AppDataTable` gets an accessible description (its placeholder, through `aria-describedby`) and a polite live announcement of how many rows came back after a search or a filter change, in every list of the app. Today its accessible name is only "Search" and nothing tells a screen reader user what the search found. Raised by F-36's screen design (owner, 2026-09-29).

## Start
- Depends on: nothing (the kit's `AppDataTable` is in `main`).
- Waits on (to start): nothing.
- Needed to validate: a screen reader (NVDA or Narrator on Windows) for the owner's listening steps; the DOM steps need none.
- Suggested path: `/agile:refine` → `/agile:build`. No `/agile:screen`: nothing visible changes (owner, 2026-10-03).
- Parallel with: any item that does not touch `Components/Ui/AppDataTable.razor`. It adds keys to `SharedResources.*.resx` (a conflict magnet: small merge conflicts expected with an item adding UI text).

## Goal
A screen reader user who types in a table's search box, or changes one of its filters, hears how many rows the table now has, and hears what the box searches by when they reach it.

## What exists today (verified 2026-10-01 and 2026-10-03)
- `src/Hosts/Simulab.Web/Components/Ui/AppDataTable.razor:20-30` — the search box is a `MudTextField` with `Placeholder="@(SearchPlaceholder ?? L["Common.Search"])"` and `aria-label="@L["Common.Search"]"`. The rendered input (bUnit probe on MudBlazor 9.9.0, not committed) is `<input ... aria-label="Search" id="mudinputbox..." placeholder="Search by name or e-mail">`: `aria-label` reaches the `<input>`, there is no `aria-describedby`, and the id is generated by MudBlazor.
- No `aria-live` region in `AppDataTable`. `AppLoadingState` has `role="status" aria-live="polite"`; `AppErrorState` has `role="alert"`; `AppEmptyState` has no live role.
- Searchable tables (7): `Admin/Users`, `Admin/AccountEvents`, `Admin/RoleHistory`, `Catalog/Exams`, `Catalog/IssuingAuthorities`, `Catalog/Organizers`, `Catalog/CatalogSearch`. All pass their own `SearchPlaceholder`. `Admin/Roles` is not searchable. The dev gallery `/dev/ui` also shows a table.
- Search reloads go through `OnSearchChangedAsync` (debounced 300 ms). Every filter outside the table (role filter in Users, account event and role history filters, the four catalog selects and "Clear filters") goes through `ReloadFromFirstPageAsync`. Paging and sorting go through the grid's own reload; the first load comes from the grid's first render.
- `.app-visually-hidden` exists in `wwwroot/app.css:634`.
- Items that touched `AppDataTable` since F-9: F-36 (initial search, page and page size; the past-the-last-page fallback). None after F-36.

## Users and use cases
- UC1 A screen reader user types in a table's search box and, once the table has reloaded, hears the number of matching rows ("12 results", "1 result", "No results").
- UC2 A screen reader user changes a filter outside the table (a select, a chip, "Clear filters") and hears the number of rows the table now has.
- UC3 A screen reader user tabs into a table's search box and hears its name ("Search") and its description (what it searches by, e.g. "Search by name or e-mail").

## Business rules
- BR1 The table announces its total row count after a load that follows a search change or a reload from the first page (`ReloadFromFirstPageAsync`). It does not announce after the first load, after a page change, after a page size change or after a sort.
- BR2 The announcement is the total count of matching rows (`TotalItems`), not the rows on the page: zero → `Common.Table.Results.None` ("No results"), one → `Common.Table.Results.One` ("1 result"), more → `Common.Table.Results.Many` ("{0} results", the number formatted in the current culture).
- BR3 A load that fails announces no count: the error state already has `role="alert"`. A load that is cancelled (a newer search replaced it) announces nothing; only the latest load's result is spoken.
- BR4 The announcement is polite (`aria-live="polite"`, `role="status"`): it waits for the screen reader to finish what it is saying and never moves the focus.
- BR5 The live region is in the page from the table's first render, empty, and visually hidden; only its text changes. A region inserted together with its text is not announced by every screen reader.
- BR6 When the box's placeholder differs from its accessible name (`Common.Search`), the box gets `aria-describedby` pointing at a visually hidden element holding the placeholder text. When they are equal (no `SearchPlaceholder` given), there is no `aria-describedby`: the reader would say "Search" twice.
- BR7 A table with `Searchable="false"` renders no description element; it still announces after `ReloadFromFirstPageAsync` (a filter outside it may exist).
- BR8 Two tables on one page get distinct ids for the description element (no repeated id: F-34's lesson).
- BR9 Nothing visible changes in any table.

## Screens and API
- No new screen, route or endpoint. The change is inside the kit component `AppDataTable`; the 7 searchable lists get it without changes of their own.
- New resource keys in `SharedResources` (pt-BR, pt-PT, en): `Common.Table.Results.None`, `Common.Table.Results.One`, `Common.Table.Results.Many`.

| Key | en | pt-BR | pt-PT |
|---|---|---|---|
| `Common.Table.Results.None` | No results | Nenhum resultado | Nenhum resultado |
| `Common.Table.Results.One` | 1 result | 1 resultado | 1 resultado |
| `Common.Table.Results.Many` | {0} results | {0} resultados | {0} resultados |

## Acceptance criteria
- AC1 Given a table with rows, when a search term is typed and the table reloads with 12 matching rows, then the live region says "12 results" (BR1, BR2, UC1).
- AC2 Given a table, when a search returns exactly one row, then the live region says "1 result"; when it returns none, "No results" (BR2).
- AC3 Given a table, when the page calls `ReloadFromFirstPageAsync` (a filter changed) and the table reloads, then the live region says the new total (BR1, UC2).
- AC4 Given a table just opened, when the first load ends, then the live region is empty; and when the user changes page, page size or sort, then the live region text does not change (BR1).
- AC5 Given a search whose load fails, when the error state shows, then the live region does not say a count (BR3).
- AC6 Given two searches typed in a row where the first load is cancelled, when the second ends, then the live region says only the second's total (BR3).
- AC7 Given any table, when it first renders, then a visually hidden element with `role="status"` and `aria-live="polite"` exists and is empty (BR4, BR5).
- AC8 Given a table with `SearchPlaceholder="Search by name or e-mail"`, when it renders, then the search `<input>` has `aria-label="Search"` and `aria-describedby` pointing at an element whose text is "Search by name or e-mail" (BR6, UC3).
- AC9 Given a table without `SearchPlaceholder`, when it renders, then the search `<input>` has no `aria-describedby` (BR6).
- AC10 Given two tables on one page, when they render, then their description and live region ids are distinct (BR8).
- AC11 Given a screen reader on `/admin/users`, when the owner types a name and then changes the role filter, then they hear the count after each one, and hear the box's description when tabbing into it (validation script, UC1-UC3).
- AC12 All new texts appear in pt-BR, pt-PT and en (missing-key test green).

## Decisions
- 2026-10-03 — Announce after a search change or a reload from the first page; not after the first load, paging, page size or sort — that is when the result really changes, and the pager would make the reader speak on every click (owner, question 1).
- 2026-10-03 — The phrase is the total count only ("132 results"), with separate keys for none, one and many — short, and the user just typed the term; whole sentences per language (rule `i18n`) (owner, question 2).
- 2026-10-03 — `aria-describedby` only when the placeholder differs from the name, avoiding "Search, Search" (owner, question 3).
- 2026-10-03 — No `/agile:screen`; only `AppDataTable` changes; no new package (owner, question 4).
- 2026-10-03 — The description points at a visually hidden element of our own (id built from a per-instance value), not at MudBlazor's generated input id — MudBlazor owns that id and may change it (Claude, technical).
- 2026-10-03 — The announcement flag is set by `OnSearchChangedAsync` and `ReloadFromFirstPageAsync` and consumed by the next successful load; the count text is written only when the load's cancellation token was not cancelled (Claude, technical).
- 2026-10-03 — Whether MudBlazor passes `aria-describedby` to the `<input>` as it does `aria-label` is verified by a bUnit test at the build (AC8); if it does not, the build stops with options (Claude, technical; project rule: an accessibility claim about a library component is verified in the DOM).
- 2026-10-01 — The item file pointed at `board: 776` (an old id); the GitHub issue of F-50 is #87, same title. Fixed to 87 (Claude, technical).

## Validation script
1. Run the app host and sign in as Admin; open `/admin/users`. → The list shows as before; nothing new is visible.
2. Open the browser's dev tools on the search box. → The `<input>` has `aria-label` "Pesquisar" and `aria-describedby` pointing at a hidden element with the placeholder text.
3. With NVDA (or Narrator) on, tab into the search box. → It says "Pesquisar" and the box's description.
4. Type part of a user's name and wait. → It says "N resultados" (or "1 resultado").
5. Type a name that matches nobody. → It says "Nenhum resultado".
6. Clear the box, then change the role filter. → It says the new total.
7. Go to the next page, then sort by a column. → Nothing is announced.
8. Open `/catalog`, pick a board in the filters. → It says the new total.
