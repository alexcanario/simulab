# Table and column descriptions

## Summary
Business descriptions on every table and column Simulab owns (`HasComment` in the EF configurations, with a migration), so the data dictionary generated by F-15 explains what each column means, not only its type and keys. The description also reaches PostgreSQL itself, so anyone who opens the database with psql or DataGrip reads it there. An architecture test keeps a new column from arriving without one. Deferred from F-15 (2026-09-21): it needs a migration and text review.

## Start
- Depends on: nothing. F-15 is done and its generator already reads the comments (`EntityModels.cs:260` and `:273`).
- Waits on: nothing — the owner answered every question on 2026-09-25.
- Suggested path: `/agile:build F-24` — no screen, and the shape is settled.
- Parallel with: F-43 (screen look) — different files.

## Goal
Make the database explain itself. Today the generated dictionary gives the type, the nullability and the keys of 272 columns and not one word about what any of them means, so the only way to understand a column is to find the code that writes it.

## What already exists
- No `HasComment` anywhere in `src/`: zero occurrences.
- DocGen already renders comments: `EntityModels.RenderDictionary` appends the entity's comment after the table name (`EntityModels.cs:273`) and `Notes` adds the property's comment to the column row (`:260`, `:401`). Nothing in the generator has to change.
- 24 tables and 272 column rows in `docs/architecture/*/data-dictionary.md`: 14 tables are Simulab's, 5 are ASP.NET Identity plumbing (`user_claims`, `user_logins`, `user_roles`, `user_tokens`, `role_claims`) and 4 are OpenIddict's, which have no configuration of ours.
- About 190 of the 272 rows are the columns every entity repeats: `id`, `tenant_id`, `created_at`, `created_by`, `updated_at`, `updated_by`, `is_deleted`, `deleted_at`, `deleted_by`.
- `TenantEntity` is not the only carrier of those columns: `User` and `Role` inherit from ASP.NET Identity and implement `IAuditableEntity, ISoftDeletableEntity` instead (the known exception in the architecture tests).
- `Job` inherits `Entity`, not `TenantEntity`, and the `jobs` table is mapped into each module context with `ExcludeFromMigrations()`, so only `JobsDbContext` emits migration operations for it.
- 19 `*Configuration.cs` files across the modules and the two building blocks that own data.

## Users and use cases
- UC1 A developer opens `docs/architecture/<module>/data-dictionary.md` and reads what each table and column means, without opening the code that writes it.
- UC2 Someone connected to the database with psql or DataGrip reads the same description from the catalog, because it is a real `COMMENT ON`.
- UC3 A developer adds a column without a description and the build tells them, naming the column.

## Business rules
- BR1 Every table Simulab owns carries a description, and so does every one of its columns. The 14 tables are: `users`, `roles`, `permissions`, `role_permissions`, `role_changes`, `account_events`, `consent_records`, `email_verification_tokens`, `password_reset_tokens`, `organizers`, `exams`, `issuing_authorities`, `jobs`, `ai_calls`.
- BR2 Tables Simulab does not define carry none: the ASP.NET Identity plumbing and the OpenIddict tables. Their meaning belongs to those libraries' documentation.
- BR3 The columns every entity repeats (`id`, `tenant_id`, `created_at`, `created_by`, `updated_at`, `updated_by`, `is_deleted`, `deleted_at`, `deleted_by`) are described once, centrally, and applied to every entity that carries them — by the `IAuditableEntity` and `ISoftDeletableEntity` interfaces and the `TenantEntity` base, so `User` and `Role` are covered too. A configuration never repeats them.
- BR4 A description is one sentence in business words. When the column stores an enum by value, it also lists what each value means.
- BR5 A description never names a feature id or a rule id: the comment lives in the database and outlives the numbering of the documents.
- BR6 Descriptions are English, like everything else in the repository (rule `naming`).
- BR7 The build fails when a column of a table under BR1 has no description, naming the table and the column. The same check fails when a table under BR1 has no description.
- BR8 The descriptions reach PostgreSQL through a migration per context that owns tables under BR1.

## Screens and API
- No screen and no endpoint: the output is `docs/architecture/<module>/data-dictionary.md`, regenerated by DocGen, and the `COMMENT ON` statements in the database.

## Acceptance criteria
- AC1 Given the model is built, when the architecture test runs, then every table of BR1 and every one of its columns has a non-empty description, and the test names any that does not.
- AC2 Given a new entity that carries the repeated columns, when its configuration adds none of them by hand, then those columns still have their central description.
- AC3 Given a column that stores an enum by value, when its description is read, then it lists what each value means.
- AC4 Given the migration is applied, when the database catalog is read (`col_description` / `obj_description`), then the table and column descriptions are there.
- AC5 Given DocGen runs, when `data-dictionary.md` is read, then each table name is followed by its description and each column row carries its own in the Notes column.
- AC6 Given the tables of BR2, when the architecture test runs, then it does not require descriptions for them, and it fails if the list of tables it checked is empty.
- AC7 Given `DocGen --check` runs after the build, then it passes: the committed dictionary matches the model.
- AC8 No new UI text: the descriptions are English only, and the localization test set is unchanged.

## Decisions
- 2026-09-25 — Only the 14 tables Simulab defines get descriptions; the ASP.NET Identity plumbing and the OpenIddict tables do not — owner — documenting another library's schema means maintaining decisions that are not ours.
- 2026-09-25 — The repeated columns are described once, centrally, and applied by convention — owner — about 190 of the 272 rows are those columns, and a copy per table would diverge.
- 2026-09-25 — The convention keys on `IAuditableEntity`, `ISoftDeletableEntity` and `TenantEntity`, not on `TenantEntity` alone — Claude, technical — `User` and `Role` inherit from ASP.NET Identity and would be missed.
- 2026-09-25 — `HasComment` with a migration, rather than a text file the generator reads — owner — it becomes a real `COMMENT ON`, so psql and DataGrip show it, and there is one place to maintain.
- 2026-09-25 — An architecture test fails the build for a missing description — owner — the same shape as the resource parity test; a warning that does not stop the build is not read.
- 2026-09-25 — One sentence per column, plus the meaning of each value when the column stores an enum by value — owner — that is what is missing to someone reading the database without the code.
- 2026-09-25 — A description carries no feature or rule id — owner — the comment is in the database and the document numbering will change.
- 2026-09-25 — Descriptions are English — rule `naming`: everything in the repository is English, and the dictionary is read by whoever develops.
- 2026-09-25 — The owner reviews the text in the generated dictionary at validation, not as a list before the code — owner — the four `data-dictionary.md` files are where the descriptions read together, and a correction there is one line of code.
- 2026-09-25 — One migration per context that owns tables under BR1 (`Identity`, `Catalog`, `Jobs`, `Ai`) — Claude, technical — each context owns its own migrations (profile), and the borrowed `jobs` mapping is `ExcludeFromMigrations()`, so no context emits another's comments.
- 2026-09-25 — No new package, in production or in tests — owner.

## Out of scope
- The ASP.NET Identity plumbing tables and the OpenIddict tables.
- Descriptions in pt-BR or pt-PT: the repository is English.
- Descriptions on indexes and constraints: PostgreSQL supports `COMMENT ON INDEX`, but EF does not expose it through `HasComment`, so it would be hand-written SQL inside the migration.
- An app manual page: nothing changes for someone using the app.
- Changing DocGen: it already reads the comments.
