# Readable entity diagrams

## Summary
The entity diagrams generated by DocGen (`docs/architecture/<Module>/entities.md`) are hard to read. They use Mermaid's default layout with curved relation lines, repeat the same eight tenant, audit and soft-delete columns in every table, write types as `character_varying_45_` and label every relation with the full foreign key name, cut at 63 characters. This feature gives them the ELK layout (right-angle lines), folds the repeated columns into one line, shortens the types and the relation labels. The owner asked for the orthogonal layout while validating B-12 (2026-09-22) and widened the scope to readability during refinement.

## Goal
One look at `entities.md` in the VS Code built-in Markdown preview shows the tables, their own columns and how they relate.

## What already exists
- `tools/Simulab.DocGen/EntityModels.cs:99-133` — `RenderEntities` writes one ` ```mermaid ` block per module: `erDiagram`, one entity per table with every column (`ColumnType` replaces every character that is not a letter, digit or `_` with `_`), then one relation per foreign key labelled with `GetConstraintName()`.
- `RenderDictionary` (same file) writes the data dictionary with every column and the full PostgreSQL type. This feature does not change it.
- `docs/architecture/Identity/entities.md`: 18 tables, 229 lines, 56 of them tenant, audit or soft-delete columns, 5 relations. `docs/architecture/Jobs/entities.md`: 1 table.
- The eight repeated columns come from `TenantEntity` (`src/BuildingBlocks/Simulab.SharedKernel/Entities/TenantEntity.cs`) and from `User`, which implements `IAuditableEntity` and `ISoftDeletableEntity` and declares its own `TenantId`: `tenant_id`, `created_at`, `created_by`, `updated_at`, `updated_by`, `is_deleted`, `deleted_at`, `deleted_by`.
- Test: `tests/Simulab.ArchitectureTests/DocGen/EntityModelsTests.cs:61-68` expects the block to contain ` ```mermaid\nerDiagram\n `; the front matter changes that.
- Items that touched this code: F-15 (created it), B-12 (JSON-owned types). F-25 (owned types sharing a table) is `building` in the worktree `wt/simulab/feature-25` and changes the same file.

### Viewers (verified 2026-09-22)
- VS Code 1.138 built-in Markdown preview (extension `mermaid-markdown-features`): Mermaid 11.17.0 with the ELK layout loaders registered. ELK routes the edges orthogonally and draws them with rounded corners (`edge.curve = "rounded"`).
- Markdown Preview Enhanced 0.8.36 (installed by the owner): Mermaid 11.17.2 without the ELK engine. `layout: elk` logs "Layout algorithm elk is not registered. Using dagre as fallback." and draws the default layout.
- In the default (dagre) layout Mermaid hard-codes `curve: "basis"` for `erDiagram` edges; no setting straightens them. ELK is the only way to orthogonal lines.
- The `erDiagram` attribute type accepts letters, digits, `_`, `-`, `[]`, `()`, `.` and `,`, no spaces (lexer rule `[\*A-Za-z_...][A-Za-z0-9\-\_\[\]\(\)\.,...]*`), so `varchar(45)` is valid. An attribute may carry a quoted comment (`"..."`).
- Azure Repos web view: not verified.

## Users and use cases
- UC1 The owner or a developer opens `docs/architecture/<Module>/entities.md` in the VS Code built-in Markdown preview and reads the tables and their relations with right-angle lines.
- UC2 Someone opens the same file in a viewer without ELK and learns from the page why the lines are curved.

## Business rules
- BR1 Every entity diagram block starts with a Mermaid front matter that selects the ELK layout (`config: layout: elk`), before `erDiagram`.
- BR2 Below the title, each entities page says in one sentence that right-angle lines need a Mermaid viewer with the ELK layout (the VS Code built-in Markdown preview) and that other viewers draw curves.
- BR3 In the diagram, the standard columns `tenant_id`, `created_at`, `created_by`, `updated_at`, `updated_by`, `is_deleted`, `deleted_at` and `deleted_by` that a table has are replaced by one line at the end of its column list, which names how many were folded and points to the data dictionary. A standard column that is part of a key or a foreign key stays in the list. A table with none of them has no such line.
- BR4 Types in the diagram use the short PostgreSQL names: `character varying(n)` → `varchar(n)`, `character(n)` → `char(n)`, `timestamp with time zone` → `timestamptz`, `timestamp without time zone` → `timestamp`, `time with time zone` → `timetz`, `double precision` → `float8`, `bit varying(n)` → `varbit(n)`. The lengths and precisions stay (`numeric(10,2)`). Any other character the diagram does not accept becomes `_`, as today.
- BR5 A relation is labelled with the foreign key column names of the dependent table, joined by `, ` (`application_id`), not with the constraint name.
- BR6 The data dictionary does not change: it keeps every column and the full type.
- BR7 The module map (`docs/architecture/modules.md`) does not change.

## Decisions
- 2026-09-22 — Target viewer: the VS Code built-in Markdown preview — it renders ELK today with no setup (owner).
- 2026-09-22 — Markdown Preview Enhanced is not configured to load ELK — it would need a script from a CDN in `.crossnote` config, fragile and outside DocGen (owner).
- 2026-09-22 — Only the entity diagrams change; the module map stays as it is — it is small and already readable (owner).
- 2026-09-22 — Each entities page carries one sentence about ELK viewers — the fallback to curves is silent and would look like a failure (owner).
- 2026-09-22 — Scope widened from the orthogonal layout to readable diagrams: fold the standard columns, short types, short relation labels — together they gain more than ELK alone, in the same file and test (owner).
- 2026-09-22 — The standard columns are recognised by their column names, not by the CLR interfaces — `User` declares `TenantId` itself and implements the interfaces directly, so names are the one signal that holds for both, and the names come from the shared kernel template (Claude).
- 2026-09-22 — The folded line is a Mermaid attribute with a comment, e.g. `standard columns "8: tenant, audit, soft delete - see data dictionary"`; the exact wording is settled at build and checked on screen (Claude).
- 2026-09-22 — No new package: ELK lives in the viewer, not in the repository (Claude).
- 2026-09-22 — F-26 is built after F-25 merges — both change `EntityModels.cs`, and F-25 is building in its worktree (Claude).
- 2026-09-22 — The missing foreign keys between `users` and the other Identity tables, found while reading the diagram, are a separate bug (B-13), not this feature — it is data integrity, not documentation (owner).
- 2026-09-22 — Approved ("aprovo F-26"). Built in the worktree `D:\dev\_icontrol\wt\simulab\feature-26` so the shared main checkout stays on `main` (owner).
- 2026-09-22 — Folded line wording: `standard columns "<n>: <groups> - see data dictionary"`, the groups present among tenant, audit, soft delete. `roles` has no `tenant_id` (7: audit, soft delete) and `jobs` only `created_at` (1: audit) (Claude, build).
- 2026-09-22 — Short types by plain prefixes, no regex table; any character an attribute type rejects still becomes `_` (Claude, build).
- 2026-09-22 — Checked before handing over: Mermaid 11 with `@mermaid-js/layout-elk` parses the new constructs (folded line with a comment, `varchar(45)`, `uuid[]`, a multi-column label) without a syntax error and routes the edges orthogonally. The VS Code preview itself is checked in the validation script (Claude, build).
