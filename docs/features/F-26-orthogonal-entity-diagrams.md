# Readable entity diagrams

## Summary
The entity diagrams generated by DocGen (`docs/architecture/<Module>/entities.md`) are hard to read. They use Mermaid's default layout with curved relation lines, repeat the same eight tenant, audit and soft-delete columns in every table, write types as `character_varying_45_` and label every relation with the full foreign key name, cut at 63 characters. The owner asked for the orthogonal layout while validating B-12 (2026-09-22) and widened the scope to readability during refinement. In v1 the Mermaid diagram got the ELK layout, but one diagram of 18 tables is about 6000 px wide and the Markdown preview shows only a slice of it. In v2 DocGen writes each module's schema as DBML (`schema.dbml`) instead, read in the dbdiagram VS Code extension: its own canvas, tables that can be moved, the standard columns folded into a table note, short types and one `Ref` per foreign key.

## Goal
One look at `schema.dbml` in the dbdiagram VS Code extension shows the tables, their own columns and how they relate.

## Users and use cases
- UC1 The owner or a developer opens `docs/architecture/<Module>/schema.dbml` in the dbdiagram VS Code extension and reads the tables and their relations.
- UC2 Someone opens the same file as text, or the `docs/architecture` index, and learns which extension draws it.

## Business rules
- BR1 DocGen writes `docs/architecture/<Module>/schema.dbml` for every module, in place of `entities.md`. The `docgen.json` key `entities` turns it on and off.
- BR2 The file starts with comment lines: generated from the EF model, do not edit, open it with the dbdiagram VS Code extension ("DBML: Open Preview to the Side"). The `docs/architecture/README.md` index says the same next to the link.
- BR3 The standard columns `tenant_id`, `created_at`, `created_by`, `updated_at`, `updated_by`, `is_deleted`, `deleted_at` and `deleted_by` are left out of a table, and the table note says `standard columns: <n> (see data dictionary)`. A standard column that is part of a key or a foreign key stays. A table with none of them has no such note. The table note also names the entity types stored in the table.
- BR4 Types use the short PostgreSQL names: `character varying(n)` → `varchar(n)`, `character(n)` → `char(n)`, `timestamp with time zone` → `timestamptz`, `timestamp without time zone` → `timestamp`, `time with time zone` → `timetz`, `double precision` → `float8`, `bit varying(n)` → `varbit(n)`. The lengths and precisions stay (`numeric(10,2)`). A type DBML does not accept bare (`uuid[]`) is quoted. A column carries `pk` (a single-column key), `not null` and `default` when they apply; a composite key is an `indexes` entry marked `pk`.
- BR5 Every foreign key is one `Ref`: `Ref: <dependent>.<columns> > <principal>.<key columns>`, with `-` instead of `>` for a one-to-one.
- BR6 The data dictionary does not change: it keeps every column and the full type.
- BR7 The module map (`docs/architecture/modules.md`) does not change.
- BR8 Every set of two or more tables linked by foreign keys is one `TableGroup`, named `<table with most dependent tables>_group`.
- BR9 An index is listed, with its name and `unique`, when every column it covers is in the file; the others are only in the data dictionary.

## Screens and API
No screen and no endpoint. The output is `docs/architecture/<Module>/schema.dbml`, regenerated by `dotnet run --project tools/Simulab.DocGen`; `--check` stays green after regeneration.

## Acceptance criteria
- AC1 (BR1) Given the real models, when the docs are generated, then `Identity/schema.dbml` and `Jobs/schema.dbml` are produced and no `entities.md` is.
- AC2 (BR2) Given any module model, when the schema is rendered, then it starts with the comment naming the dbdiagram extension; and the README links each module's `schema.dbml` with the same hint.
- AC3 (BR3) Given the Identity model, when the schema is rendered, then no table lists `created_at`, `created_by`, `updated_at`, `updated_by`, `is_deleted`, `deleted_at`, `deleted_by` or `tenant_id` as a column, and the notes of `users` and `consent_records` say `standard columns: 8 (see data dictionary)`.
- AC4 (BR3) Given a table without standard columns (an OpenIddict table), when the schema is rendered, then its note has no `standard columns`.
- AC5 (BR4) Given the Identity model, when the schema is rendered, then it shows `ip_address varchar(45)` and `accepted_at timestamptz [not null]`, contains neither `character varying` nor `with time zone`, and `role_permissions` has `(permission_name, role_id) [pk]`.
- AC6 (BR5) Given the OpenIddict tables, when the schema is rendered, then it has `Ref: openiddict_tokens.application_id > openiddict_applications.id` exactly once, and no `fk_` name.
- AC7 (BR6) Given the Identity model, when the data dictionary is rendered, then it still lists `created_at` with type `timestamp with time zone`.
- AC8 (BR1-BR5) Given the committed `docs/architecture/`, when `dotnet run --project tools/Simulab.DocGen -- --check` runs after the regeneration, then it exits 0.
- AC9 (UC1, screen) Given the regenerated `Identity/schema.dbml` opened in the dbdiagram VS Code extension, then it opens without a parse error and the tables and relations are readable (validation script).
- AC10 No UI text is added: the generated docs are English and outside the app, so the resource files do not change.
- AC11 (BR8, BR9) Given the Identity model, when the schema is rendered, then it has `TableGroup users_group` with 12 tables and `TableGroup openiddict_applications_group` with 3, and no index names a column left out of its table.

## Decisions
- 2026-09-22 — Target viewer: the VS Code built-in Markdown preview — it renders ELK today with no setup (owner). Superseded by v2: the dbdiagram VS Code extension.
- 2026-09-22 — Markdown Preview Enhanced is not configured to load ELK — it would need a script from a CDN in `.crossnote` config, fragile and outside DocGen (owner).
- 2026-09-22 — Only the entity diagrams change; the module map stays as it is — it is small and already readable (owner).
- 2026-09-22 — Each entities page carries one sentence about ELK viewers — the fallback to curves is silent and would look like a failure (owner). Superseded by v2: the comment at the top of `schema.dbml`.
- 2026-09-22 — Scope widened from the orthogonal layout to readable diagrams: fold the standard columns, short types, short relation labels — together they gain more than ELK alone, in the same file and test (owner).
- 2026-09-22 — The standard columns are recognised by their column names, not by the CLR interfaces — `User` declares `TenantId` itself and implements the interfaces directly, so names are the one signal that holds for both, and the names come from the shared kernel template (Claude).
- 2026-09-22 — No new package: the diagram is drawn by the viewer, not by the repository (Claude).
- 2026-09-22 — F-26 is built after F-25 merges — both change `EntityModels.cs` (Claude).
- 2026-09-22 — The missing foreign keys between `users` and the other Identity tables, found while reading the diagram, are a separate bug (B-13), not this feature — it is data integrity, not documentation (owner).
- 2026-09-22 — Approved ("aprovo F-26"). Built in the worktree `D:\dev\_icontrol\wt\simulab\feature-26` so the shared main checkout stays on `main` (owner).
- 2026-09-22 — v1 build: Mermaid 11 with `@mermaid-js/layout-elk` parsed the v1 constructs and routed the edges orthogonally, but the whole Identity diagram was 6016 px wide. Splitting it into one diagram per group was measured (680 to 1002 px each) and set aside for DBML (owner).
- 2026-09-22 — DBML replaces the Mermaid page instead of living next to it — two diagrams of the same schema would be two things to keep readable (owner, v2).
- 2026-09-22 — No DBML parser in .NET: the tests check the generated text; the parse is checked in the extension, in the validation script (Claude, v2).
