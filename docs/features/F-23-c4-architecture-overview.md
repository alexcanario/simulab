# C4 architecture overview

## Summary
A one-page hand-written architecture overview in Mermaid: C4 context (students, curators, admins, Claude API, email) and containers (Web, Api, PostgreSQL, Redis, file storage). It sits beside the generated docs of F-15, outside `docs/architecture/`, which DocGen owns. Deferred from F-15 (2026-09-21): more useful once more modules exist (Catalog has shipped since).

## Goal
Anyone opening the repository sees in one page who uses Simulab, what it talks to and which processes and stores it runs, without reading the app host or the ADR. A test keeps the page honest when the app host changes.

## What already exists (verified 2026-09-24)
- `docs/architecture/` is generated by `tools/Simulab.DocGen` (F-15). **Every file in that folder that DocGen does not produce is reported stale by `--check` and deleted on the next run** (`tools/Simulab.DocGen/GeneratedDocs.cs:23-32`, `:49-51`). The summary's premise "next to the generated docs, outside the files DocGen overwrites" is false inside that folder: the page must live elsewhere.
- `docs/architecture/modules.md` (generated) already shows the module and project references: the component level of C4.
- The app host (`src/Hosts/Simulab.AppHost/AppHost.cs`) starts: `postgres` (database `simulab`), `mailpit`, `redis`, `api`, `web`. Web references Api and Redis; Api references PostgreSQL, Mailpit and Redis. Google sign-in is configured only when the OAuth client is in user secrets (F-20).
- Not built yet: `IAiGateway` / Claude API, `IFileStorage` / Azurite (`docs/infra.md`: "Planned, added by the first feature that needs it"). No reference to either in `src/`.
- Database schemas: `identity`, `catalog`, `jobs`. The job worker runs inside the Api host.
- Seed roles: Student, Curator, Admin (`Roles.All`).
- Items that touched this area since F-15: F-26 (DBML entity diagrams), F-33 (Catalog module), B-15 (route map regenerated).

## Users and use cases
- UC1 A developer (or Claude) opens `docs/architecture-overview.md` and sees the system context: the three roles, Simulab, and the external systems with their state (built, planned, optional).
- UC2 A developer sees the containers: Web, Api, PostgreSQL, Redis, file storage, and the email provider and Claude API they reach, with what travels on each arrow.
- UC3 A developer who changes the app host (adds, renames or removes a resource) gets a failing architecture test until the overview matches.

## Business rules
- BR1 The overview lives at `docs/architecture-overview.md`, outside `docs/architecture/`; `CLAUDE.md` (Architecture) and `docs/infra.md` (Technical docs) link to it.
- BR2 Two diagrams, Mermaid `flowchart` with the C4 colours: system context and containers. The component level is a link to the generated `docs/architecture/modules.md`, not redrawn.
- BR3 Something decided but not built (Claude API, file storage) is drawn dashed and labelled `planned`. Something built but off by default (Google sign-in) is dotted and labelled `optional`.
- BR4 Every resource the app host starts appears as a node of the containers diagram, with the resource name as the node id (`web`, `api`, `postgres`, `redis`, `mailpit`).
- BR5 A node marked `planned` is not an app host resource: when it is built, the test fails until the mark is removed.
- BR6 Each diagram fits an IDE Markdown preview (about 736 px of content) without scaling below 95 %.

## Acceptance criteria
- AC1 (BR1) Given the repository, when a developer opens `CLAUDE.md` or `docs/infra.md`, then each links to `docs/architecture-overview.md`, and `DocGen --check` stays green (nothing added under `docs/architecture/`).
- AC2 (UC1, BR2, BR3) Given the overview, when it is rendered, then the context diagram shows Student, Curator and Admin, Simulab, the email provider, the Claude API (dashed, planned) and Google (dotted, optional).
- AC3 (UC2, BR2, BR3) Given the overview, when it is rendered, then the containers diagram shows Web, Api, PostgreSQL, Redis and file storage (dashed, planned) inside Simulab, plus the email provider and the Claude API, and links to `docs/architecture/modules.md` for the modules.
- AC4 (UC3, BR4) Given an app host resource that is not a node of the containers diagram, when the architecture tests run, then `ArchitectureOverviewTests` fails naming the resource.
- AC5 (BR5) Given a node marked `planned` whose id is an app host resource, when the architecture tests run, then the test fails naming the node.
- AC6 (BR6) Given each diagram rendered with Mermaid 11 at a 736 px content width, when its natural width is measured, then it is at most 775 px (scale ≥ 95 %). Checked on screen, in the validation script.
- AC7 (localization) No UI text changes: no resource file is touched, and the app manual is unchanged (a developer page, no visible behavior).

## Decisions
- 2026-09-24 — The page is `docs/architecture-overview.md`, linked from `CLAUDE.md` and `docs/infra.md` — owner: DocGen deletes hand-written files inside `docs/architecture/`; changing DocGen would touch the plugin template and F-15's contract.
- 2026-09-24 — Claude API and file storage are drawn dashed and labelled `planned` — owner: shows what ADR-0001 decided without pretending it exists; the guard removes the mark when they are built.
- 2026-09-24 — Context and containers only; the component level links to the generated `modules.md` — owner: a hand-drawn copy would drift at every new module.
- 2026-09-24 — Mermaid `flowchart` with the C4 colours, not the experimental `C4Context` syntax — owner: renders in VS Code, Rider and Azure DevOps, and was measured in the prototype.
- 2026-09-24 — A drift guard, `ArchitectureOverviewTests`, compares the containers diagram with the app host — owner: a hand-written diagram ages silently; the definition of done asks for a test per criterion.
- 2026-09-24 — B-15's file still says `validating` although it is merged and its board item is closed; it is finished later by `/agile:ship B-15` in another session, not in this run — owner.
- 2026-09-24 — Approved by the owner ("Aprovo F-23") at autopilot stop 1.
- 2026-09-24 — Google appears only in the context diagram; the containers diagram leaves it out — decided by Claude: it is optional and off by default, and one more node on the bottom rank pushed the diagram past the preview width (measured 973 px before, 745 px after).
- 2026-09-24 — The containers diagram hangs the external systems one rank below the stores (`--->`) — decided by Claude: with five nodes on one rank the diagram measured 973 px; with the extra rank, 745 px.
- 2026-09-24 — No new package: Mermaid is rendered by the viewer (IDE preview, Azure DevOps); the test uses the existing xUnit and AwesomeAssertions — decided by Claude.
- 2026-09-24 — The guard reads resource names from `AppHost.cs` text (`builder.Add<Kind>("name"`), skipping `AddParameter` — decided by Claude: loading the Aspire model in a unit test would start DCP; the text is enough for names.
