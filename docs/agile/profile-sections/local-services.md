Quiz question 3a writes `- Local services: fixed` under `Profile:` in `CLAUDE.md`; `none`, or no line, leaves the AppHost as the recipes below write it. With `fixed`, every container the AppHost declares for a local run (today the database; a container added later follows the same rule) keeps its address, its password and its data from one `aspire run` to the next, so a saved DataGrip or pgAdmin connection keeps working (measured on Aspire 13.6.1, PostgreSQL 18.3, a scratch AppHost run twice):
- Port: the host port is the image's default (PostgreSQL 5432, SQL Server 1433, pgAdmin 5050, Redis 6379, RabbitMQ 5672), or the next free one when the bootstrap finds it in use, passed as the `port:` argument of `AddPostgres` / `AddSqlServer`, only outside publish mode (in publish mode it would publish the database on the host). The container itself still gets a new internal port on every run; the client connects to the fixed one, which Aspire's proxy forwards.
- Password: `builder.AddParameter("<resource>-password", secret: true)` (`postgres-password`, `sql-password`) outside publish mode; publish mode keeps `dbpassword` of the recipes, so no deploy changes. The bootstrap generates the value (random, 22 or more letters and digits) and writes it with `dotnet user-secrets set "Parameters:<resource>-password" <value> --project <AppHost>`: never printed, never written to a file of the repository, never in `CLAUDE.md`. The AppHost keeps its `UserSecretsId` and its `launchSettings.json` with `DOTNET_ENVIRONMENT=Development` (the template's: without the Development environment user secrets are not read and the parameter stays `ValueMissing`). The owner reads it with `dotnet user-secrets list --project <AppHost>`. User secrets live in the user profile, so every worktree of the repository shares them; a clone on another machine runs the same `set` with its own value, and until then the resources that use it stay `Waiting`.
- Volume: `WithDataVolume()` outside publish mode. The image applies the password only when its data is created: a changed secret against an existing volume fails with `password authentication failed` (measured). To change it, remove the volume (`docker volume ls` shows `<apphost>-<hash>-<resource>-data`, `docker volume rm <name>` removes it) and the data in it. The name carries a hash of the AppHost's path, so a worktree has its own volume with its own data, on the same fixed port: one app host at a time.
- More than one API in the solution: the bootstrap proposes a free start (such as 5100) and each API takes the next port in the order of the solution, as the `http` `applicationUrl` of its `launchSettings.json`, the `https` one at the same port + 1000. One API, or none: the ports `dotnet new` chose stay.
- `docs/infra.md` gets `## Local services`: one row per service with its host port, the user-secrets key of its password and its volume, never a value, and the reset command above.
```csharp
// <App>.AppHost/Program.cs, instead of the database line of the recipes (SQL Server: AddSqlServer("sql", password: ..., port: ...), "sql-password", 1433)
var publish = builder.ExecutionContext.IsPublishMode;
var postgres = builder.AddPostgres("postgres", password: publish ? builder.AddParameter("dbpassword", secret: true) : builder.AddParameter("postgres-password", secret: true), port: publish ? null : 5432);
if (!publish) postgres.WithDataVolume();
var database = postgres.AddDatabase("appdb");
```
In the Azure recipe the container branch of `database` is the same block (`compose` in place of `publish` for the password), and the managed branch stays as it is.
