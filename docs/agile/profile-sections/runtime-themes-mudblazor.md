- Applies only when `docs/design/themes/` exists (written by `themes.js write --init`, `references/theme-format.md`; the bootstrap question 23f runs it); the kit item builds the module with the kit, and an item that adds it to an existing kit follows the same text. It lives in the web host project (`<App>.Web`, folder `Theming/`), never in Core, Domain or `<App>.Shared`; the staff backoffice of `mobile` keeps the identity only. The module follows "Run-time rules shared by the kits" in `references/theme-format.md` (font stack, unknown and unmapped keys, contrast minimum by type, hand-dropped files, alpha order, a locked key on the page, the theme selector); this section adds only what MudBlazor needs.
- Catalog: the web host links the project's own files as content, one source and no copy (`<Content Include="..\..\docs\design\themes\*.json" Link="themes\%(Filename)%(Extension)" CopyToOutputDirectory="PreserveNewest" />`, the path adjusted to the project's depth). At startup it reads `index.json` (`themes`, `defaults`, `locked`, `contrast`) for the built-in themes, and every other file of the folder as a user theme by the hand-dropped rule (BR7 of the shared rules). An index or built-in file with a `formatVersion` above 1 is refused naming the file and the version and stops the startup; fields the module does not know are ignored. The host reads the theme files from `<AppContext.BaseDirectory>/themes` and never serves them over HTTP (no static-file mapping of that folder): `/themes/index.json` answers 404, by design. The catalog is a singleton loaded once after `builder.Build()` and before `app.Run()` (`app.Services.GetRequiredService<ThemeCatalog>().Load()`), so `ILogger` exists; a built-in theme the index lists that cannot be read stops the startup with a `ThemeFormatException`.
- Keys: one table `ThemeKeys` maps each theme key to a `MudTheme` palette property; the run-time service and the palette test read that same table. With the identity's eight default roles (the `color` group dropped) it is: `primary` → `Primary`, `secondary` → `Secondary`, `background` → `Background`, `surface` → `Surface`, `text` → `TextPrimary`, `error` → `Error`, `success` → `Success`, `warning` → `Warning`. An app with its own keys has the kit item map each of them and list in the item the keys it leaves unmapped. A key the default theme has with no entry is an unmapped key (BR4 of the shared rules): the service ignores it and the page lists it under "Unmapped keys". Where `docs/design/themes/` exists, the palette test of the kit sentence compares the kit's palette with the generated default theme files (`<theme>-light.json`, `<theme>-dark.json` of `docs/design/themes/`) through `ThemeKeys`, not with the DTCG tokens (no DTCG parser in C#).
- Settings: `AppearanceSettings` is one JSON object in the browser's `localStorage` under the key `appearance`, on the device only (nothing goes to the server, no cookie): `formatVersion` 1; `mode` (`system` by default, `light`, `dark`); `light` and `dark` (the preferred theme ids); `colors` (key → `#RRGGBB` or `#RRGGBBAA`, or `"default"`, for every theme); `themes` (theme id → the same map, for one theme); `font` (`family`, `size`). It is read in `OnAfterRenderAsync(firstRender)`, because JS interop does not exist during prerender: the first paint uses MudBlazor's default theme until the circuit starts (measured). A missing or unreadable value, a higher `formatVersion` or blocked storage gives the defaults and never throws.
- Resolution: the active theme is the preferred theme of the mode (`system` asks `MudThemeProvider.GetSystemDarkModeAsync()` after the first render, and again each time the mode becomes `system`); an id the catalog no longer has falls back to `defaults.light` or `defaults.dark`. Colors resolve in this order: the theme's own, a key it leaves out from the default theme of its type, the all-themes `colors`, then the one-theme `themes[id]`. `"default"` sets the key back to what the theme itself resolves, in the map that holds it: in `colors` it clears the key for every theme, in `themes[id]` it restores the theme's value even over an all-themes override (measured). A `locked` key ignores any customization.
- Provider: `MudThemeProvider` takes `IsDarkMode` from the module (true when the active theme's type is dark, whatever the mode, so a dark theme chosen as the preferred light one still fills `PaletteDark`) and `ObserveSystemDarkModeChange` is true only while `mode` is `system`; `IsDarkModeChanged` (MudBlazor 9.11.0 has no `SystemDarkModeChanged`) feeds the module's system state. The `MudTheme` is rebuilt from the resolution on every change, without a reload.
- Font: `font.family` keeps ASCII letters, ASCII digits, space, `-`, `_` and `.` (anything else is dropped), is trimmed, then cut at 64 characters, and becomes the first name of the font stack of the shared rules (BR2: then the identity's `typography.body` list, then `system-ui`, `sans-serif`, a repeat left out), set on every `Typography` entry (`Default`, `H1` to `H6`, `Body1`, `Body2`, `Subtitle1`, `Subtitle2`, `Button`, `Caption`, `Overline`), not only `Default`; empty keeps the identity's. `font.size` is an integer from 12 to 24 px (16 by default, clamped), set as `document.documentElement.style.fontSize`, so every rem-based style scales together (an `h4` of 2.125rem is 42.5px at 20px). No font file is packaged.
- Contrast: for the active theme, and for a user theme when it is chosen, the module computes the WCAG 2.2 ratio of every pair of `index.json`'s `contrast` over the resolved colors, with the helper the palette test already uses (one helper, no copy), and returns the failing pairs (foreground, background, ratio cut to two decimals, the minimum of the theme's type: BR5 of the shared rules). The page shows them as a warning list; the module never refuses, saves less or applies differently because of it.
- Page: the route `/appearance` is open to any visitor (no sign-in, no API call; the `website` public layer included), linked from one place of the layout. Controls: mode, preferred light theme, preferred dark theme, font family, font size, a color field per mapped key of the active theme (its resolved keys: its own and the fallback), restore all, the unmapped keys of the active theme (listed, with no field), and a read-only JSON view of the customization with a copy button. Each key is a text field with a swatch; only a valid hex reaches the theme (an invalid text is shown as an error under the field and not stored). An edit writes `themes[<active id>]`; a switch "Apply to all themes" (a resource), off by default, sends the edits to `colors` instead. Restore removes the key from the map the switch names, and writes `"default"` in `themes[<id>]` when `colors` holds that key. A locked key shows its value and its lock icon, read-only, with no restore action (BR13 of the shared rules). Restore all writes the settings defaults: `mode` `system`, `light` and `dark` null (resolved to `defaults.light` and `defaults.dark`), `colors` and `themes` empty, `font` empty; the stored user themes (`appearance.themes`) are untouched. The theme lists show each theme's `name`, which is also its accessible name (a display function, never a record's default `ToString`: BR14). Its texts are resources of each locale of `UI locales:`; theme names come from the files and are not translated. It is a kit pattern shown on the gallery with its states: default, contrast warnings, no customization, a locked key, a long theme name that wraps.
- Details the rebuild from this text settled: the log is `ILogger`, warning level. A `type` ending in `dark` uses `PaletteDark`, every other (`light`, `hc-light`) `PaletteLight`, and the other palette stays MudBlazor's; the file's own `id` wins over the index entry's. `ThemeKeys` lives in `Theming/`: `Func<Palette, MudColor>` get and `Action<Palette, MudColor>` set accessors (`using MudBlazor.Utilities;`; a `string` property such as `OverlayDark` is converted with `MudColor.ToString(MudColorOutputFormats.HexA)`) and a constant list `IdentityFontFamilies` from the identity's `typography.body`, because theme files carry no typography. A theme's keys fall back by the theme's own `type`; the preferred light and dark lists show only themes of that type, but resolution accepts any id. `hc-light` counts as light and `hc-dark` as dark for that fallback and for the preferred lists, and every theme, built-in or user, of type `hc-*` is checked against `minHighContrast`, any other against `min` (BR5 of the shared rules). A `locked` key keeps the default theme's value: a customization is ignored, and a user theme's own different value is dropped when the theme is read (BR7 of the shared rules). An invalid color value (not hex) is ignored and the key keeps its value below; `"default"` on a key the theme leaves out gives the fallback value. A settings object that fails to deserialize gives the defaults as a whole; an unknown `mode` alone becomes `system`. Until `GetSystemDarkModeAsync()` returns, `system` counts as light. The contrast helper lives in the web host (the service and the palette test both call it), works on the RGB bytes (alpha ignored), skips a pair whose key is missing and cuts the ratio down (floor), and the warnings are computed on the resolved colors, so a customization that breaks a pair is listed too. Blocked storage is a storage abstraction (`IAppearanceStorage`) that tests replace; the page shows an info alert when a write fails. The layout hosts `MudThemeProvider`, `MudPopoverProvider`, `MudDialogProvider` and `MudSnackbarProvider` in one component of `Theming/` that needs `AddMudServices()` and the interactive server render mode on `Routes` and `HeadOutlet`. A bUnit test that renders MudBlazor disposes with `await using var ctx = new BunitContext()`, not by inheriting the class (`PointerEventsNoneService` only implements `IAsyncDisposable`).
- Tests (no browser): the resolution order, `"default"` in both maps, a locked key, an unknown id, a higher `formatVersion` of the index, a failing pair listed, the font filter, the font stack and the size clamp, the settings round trip and blocked storage, Restore and Restore all, the option text of the theme lists (bUnit), and the hand-dropped files (one test per fixture of the plugin's `scripts/fixtures/themes/import/`, copied into the test project, with its `themes/` as the built-in folder: the oracle `themes.js import` on the same file gives the kept keys or the refusal, and the id is the file's own as written); `Theming:RefuseFailingContrast` (default false) is the kit item's, read at startup and by the import; the palette test keeps passing through `ThemeKeys`. The live follow of an OS change is not measured by the browser pane (its emulation raises no `change` event): the validation script asks the owner to flip the OS setting once.

### Import and generate
- Built by a second item, "Import and generate themes in the MudBlazor kit", never by the kit item; the rules are written once in `references/theme-format.md`, "User themes: import and generate" (refusals, report, stored form, id, cap, generate, export, remove), and the item's tests carry the runs of `themes.js import` shown there.
- Storage: the browser's `localStorage` key `appearance.themes`, `{ "formatVersion": 1, "themes": [ <stored theme> ] }`, beside `appearance` and read with it in `OnAfterRenderAsync`; "Restore all" leaves it. At most 20 stored themes. The server folder `<AppContext.BaseDirectory>/themes` is never written and its theme wins over a stored one of the same id. An unreadable or blocked key gives an empty list; a failed write is an info alert and nothing is stored.
- Controls on `/appearance`: "Import theme..." (`InputFile` with `accept=".json"`, opened with `OpenReadStream(maxAllowedSize: 65536)`, so a larger file is refused before its text is read), "Generate from my customizations" (disabled while the theme shown has no customization; a name field, `<base name> (custom)` by default), a "Your themes" list with "Download" (`<id>.json` as a blob through JS interop) and "Remove" (after a confirmation) on each stored theme, and a result area with the report or the refusal. Built-in and server-folder themes have no "Remove". A stored theme joins the lists at once, with no reload.
- Tests (no browser): the reference's runs, the 64 KiB stream and the 10,000-level file, the cap of 20, an id taken by a built-in, a server-folder theme over a stored one, generate (every resolved key, a locked key at its default, the settings unchanged), export then import again, remove of the preferred theme, a name with markup rendered as text, and a resource for every label, reason and report line in each locale.
